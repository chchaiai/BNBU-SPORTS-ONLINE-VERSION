# 学生跨浏览器打卡历史读取修复

## 复现与范围

本地真实 HTTP / PostgreSQL 的合成学生账号，在全新浏览器中能够取得服务端记录。向待提交运动恢复接口注入 503 后，原工作区加载返回失败，已提交记录未写入页面，记录列表为零。已有浏览器内存中的工作区则可能仍保留旧记录，造成换浏览器或清缓存后历史消失的表现。

这是已复现并修复的失败路径；没有取得用户实际故障的生产请求，因此不认定它是该线上事件的唯一原因。

另发现记录接口同时返回草稿，前端按页过滤后，若首页全部为草稿，会展示空列表，已提交历史藏在后续页。

## 修改

- 待提交运动恢复失败独立提示，不再阻断整个工作区；认证和权限错误仍正常传播。
- 进入记录页独立向服务器查询本人历史，提供刷新与重试，不依赖本机缓存或其他工作区模块成功。
- 自动跳过仅有草稿等不可展示记录的页面，保留后续分页游标，并限制重复游标和最大页数。
- 加载和错误状态不显示“暂无记录”；分页去重，异步响应检查登录代次，退出或换账号后不回填原账号数据。

## 验证

- 新增针对性测试 5 项通过，覆盖空工作区恢复、草稿分页、失败重试、退出竞态、分页去重与游标循环。
- 学生端测试合计 85 项通过，烟测 87 项通过。
- 真实本地 HTTP / PostgreSQL 移动浏览器：全新上下文、清空 localStorage/sessionStorage 后重载并恢复认证、待提交恢复接口 503、记录接口 503 后重试均通过，无页面运行错误。
- 浏览器使用本地测试邮箱验证码建立会话；图片原图 IndexedDB 的清理不属于本次已提交记录列表验证。
- `git diff --check` 通过。

证据：`evidence/record-history-20260918/browser.json` 和页面截图。回归脚本为 `tools/local-integration/record-history-browser.mjs`，依赖复用模式下的本地 `demand-six-server.mjs` 与现有含已提交记录的合成账号。

## 生产发布

用户追加授权“修复后部署”后，发现线上固定基线为 `zero-target-20260918`，其两个学生模块早于本地 HEAD，未包含本地待提交恢复模块。本次发布以线上完整学生站为基线，只叠加独立历史读取、分页和加载/重试显示；本地工作区的待提交恢复容错改动不属于线上发布包。

实际候选包额外通过 7 项针对性测试及真实本地服务浏览器验收。向活动认证接口注入 503 可使旧版工作区为空，但进入记录页仍可从真实服务恢复历史；全新浏览器、清缓存、记录查询失败后重试均通过。候选证据见 `evidence/record-history-20260918/candidate/browser.json`。

已发布 `/opt/bnbu-sports-production/releases/record-history-20260918`，保留 `zero-target-20260918` 回滚目录。两个线上模块的普通 URL 和带版本参数 URL 摘要均匹配；学生站、两域 readiness 正常；容器 ID、镜像及启动时间未变化；未认证历史请求返回 401。本机再次公网核验通过。

仅更新学生 Web 的 `api.js` 和 `screens/checkin.js`，无数据库迁移或历史记录改写。真实业务读取验收使用本地合成账号；未代登录生产真实学生账号。发布摘要与结果见 `manifest.json`、`deployment.json`，打包及发布脚本位于 `tools/production/`。
