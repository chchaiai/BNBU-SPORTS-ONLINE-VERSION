# 学生扫码先验证邮箱：实现与部署交接

日期：2026-09-14。用户授权修改并部署；已确认已登录且学校邮箱已验证的学生复用验证状态。

## 最终行为

扫码或输入邀请码 → 验证学校邮箱 → 填写/确认学生信息 → 正式入班。已登录且学校邮箱已验证者直接确认信息。

首次验证只消费验证码并产生受邀请约束的加密凭证，不提前创建账号、会话或成员关系。正式入班在事务内核对邀请、邮箱归属、学生身份、完整资料和同学期唯一班级，再创建已验证的 ACTIVE 账户、成员关系和会话。已登录学生复用本人身份；不能仅凭姓名、学号或未验证邮箱接管已有账户。旧匿名凭证不能绕过前置验证。

邀请撤销、班级关闭、学期归档和系统维护等限制继续生效。邀请到期前完成邮箱验证的同一流程可使用既有 10 分钟宽限；重试遵循原有幂等键，不延长有效期。

## 接口与数据库

1. `POST /api/v1/auth/student-sign-in-codes`：复用 EMAIL 验证码发送及现有发送限流。
2. `POST /api/v1/auth/student-sign-in-codes/verify`：入班时增加 `joinInviteToken` 与 `joinEmail`。成功返回 `joinEmailProof`、`expiresAt` 和已验证邮箱所有者的 `profile`（首次注册为 null）。不携带入班参数时保留普通登录行为。
3. 匿名或已登录入班凭证接口在信息确认后接收 `joinEmailProof`。已登录且学校邮箱已验证时可省略该字段。
4. 正式 `/course-invites/{token}/join` 继续使用原有凭证、幂等键和响应结构。资料不足或校验失败不创建成员关系。

复用现有验证码、入班凭证、用户、学生档案、会话及成员表；没有新增数据库迁移。邮箱验证事实和入班审计在正式入班事务中记录。OpenAPI 源文件及运行时生成文档同步更新。

## 验收边界与后续

浏览器自动化当前环境不可用，因此没有声明真实浏览器扫码、学校邮箱实际收件或安卓实体设备验收。本地邮件投递使用隔离测试服务，生产验证只读取状态与静态文件，不创建虚假学生。原生安卓客户端如独立实现入班页面，需要按上述接口补充前置邮箱步骤；本次发布对象为后端与学生网页，未生成 APK。

已验证账号复用以服务端当前状态为准。未验证的历史账号若无原登录会话仍需可信账号恢复，不允许用新邮箱加学号自动合并。学校邮箱识别复用仓库现行业务规则。旧页面若缓存或保持打开，应刷新后开始新的扫码流程。
