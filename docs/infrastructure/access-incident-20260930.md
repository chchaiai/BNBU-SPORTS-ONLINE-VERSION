对象：`www.student.bnbusports.cn`、`www.teacher.bnbusports.cn`；香港 CVM `ins-kfitq8i6 / 43.129.193.7`；数据库 `postgres-entm7byh`。全部事件时间使用北京时间。

主要故障窗口为 07:00–10:50，随后根据用户补充检查 10:50–10:56。用户反馈：校园网 Wi-Fi 慢，宿舍非校园网快，中国移动手机流量慢；10:52 左右安卓 Edge 出现首页白屏等待。

## 判断及证据边界

现有证据最支持的问题位置是客户端到香港源站的连接与传输路径。不同网络的速度对照、服务器快速响应、静态小文件数秒等待和部分连接的重传互相吻合。尚未获得故障手机的浏览器请求时间线和同一网络的 DNS、TCP、TLS、路由测量，不能把具体根因定为某个运营商节点、校园网设备、DNS 故障或某一种丢包机制，也不能声称故障已经消除。

已确认存在自动漏洞扫描；主要扫描组的请求全部返回 404，强度和同时段资源变化不支持它造成持续慢访问。腾讯云攻击分析页面在覆盖今天的 7 天内显示攻击与封堵事件均为 0。此结果代表该产品检测并记录的事件，不等于互联网上完全没有恶意请求。

没有发现持续 CPU、磁盘、出口带宽、连接数耗尽，或应用重启、OOM、数据库长时间阻塞的证据。另发现两个会放大弱网等待的前端加载问题：学生入口预加载大量脚本，教师工作区启动时按记录逐条请求多份数据。这两项属于已确认的加载成本，当前证据不足以把它们单独认定为 10:52 首次白屏的原因。

## 已确认的页面加载成本

教师 10:52 启动请求中有 25 次 `getExerciseRecord`、25 次 `getExerciseRecordEvidenceContext`、25 次 `listExerciseRecordReviews`。与 `teacher-data.ts:1003` 的 `loadSubmittedCheckins` 完全吻合：先列记录，再为每条记录并发发起 3 个请求。`teacher-workspace.tsx:1585` 起还依次等待课程、学生、记录，再加载成绩和豁免。请求数量随记录数增加，且存在多轮网络往返。

学生线上 HTML 引用/预加载 50 个不同 JS 地址（含 runtime-config）及 6 个 CSS 地址。HTTP/2、gzip、版本资源长期缓存当前有效，但首次访问仍要获取脚本依赖。模块数量和启动依赖会增加弱网下的首次等待，不能因为设置了缓存就认为首次访问问题已经解决。

这些发现支持下一轮按以下优先级处理：

1. 在同一台设备上对校园网、中国移动、宿舍网络交替测量同一 URL，收集 DNS、TCP、TLS、首字节、脚本下载与首次绘制，并与服务器时间对齐；核查代理/TUN，防止把代理链路当成直连。
2. 教师端先显示框架和必要列表，记录详情/凭证/审核按需加载，必要时再设计批量接口；学生端缩小首屏脚本依赖。业务与权限规则应在专项修复中回归验证。
3. 若慢网络的连接/传输瓶颈被对照确认，再评估静态资源边缘缓存及动态链路加速，或靠近主要用户的部署方案。先用可撤回测试域名验证；目前没有依据直接扩大 CPU、内存或采购高防。
